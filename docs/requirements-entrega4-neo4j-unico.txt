# REQUIREMENTS — Entrega 4: Neo4j como backend único + dependências embutidas no compose

**Repo:** `/opt/containers/zrouter` (raiz), código em `./app`
**Ambiente dev:** container na porta 20129. **PRODUÇÃO em 20128 — NÃO TOCAR.**

---

## CONTEXTO / DECISÕES DO DONO

1. **Só Neo4j.** O backend Hindsight não deve ir para o ZRouter — consome tokens demais
   (ele sintetiza/resume memória via LLM). O ZRouter usa **exclusivamente Neo4j** para memória
   de identidade. O suporte a Hindsight deve ser **removido do ZRouter**; qualquer chave
   configurada com `memoryBackend: "hindsight"` deve migrar/fallback para `neo4j`.
2. **Dependências embutidas no compose.** O `docker-compose.yml` do ZRouter deve trazer o
   Neo4j (e demais fontes) **já declarados**, de forma que clonar + `docker compose up -d`
   já suba o que é necessário. Hoje elas estão atrás do profile `extras` e o core não as traz.

## ⚠️ RESTRIÇÃO CRÍTICA DE AMBIENTE (leia antes de mexer no compose)

Neste servidor **já existe um Neo4j de produção rodando**:

- container `neo4j` (imagem `neo4j:5.26-community`), `Up` há dias, **healthy**
- compose em `/opt/containers/neo4j/docker-compose.yml` (projeto `neo4j`)
- já publica `0.0.0.0:7474` e `0.0.0.0:7687`
- contém ~30k nós `Memory` e o bank `ViniciusMathias` — **dados reais, insubstituíveis**

O `docker-compose.override.yml` local do ZRouter já injeta as credenciais desse Neo4j no
container do zrouter. Se o compose embutido tentar subir um segundo Neo4j na mesma porta,
o `up` quebra ou derruba o serviço de produção.

**Solução obrigatória:** as dependências do compose ficam atrás do profile **`bundled`**
(opt-in) e os `depends_on` usam `required: false`. Assim, `docker compose up -d` neste
servidor sobe **somente o zrouter**, que continua falando com o Neo4j de produção via
`NEO4J_HTTP_URL`. Detalhes completos e comandos de verificação na **Parte C**.

Não use o override para "desativar" serviços — o profile resolve isso de forma portável
(funciona em qualquer máquina, não só nesta).

## PARTE B — Criar o Bank no Neo4j de verdade (pedido do dono)

Hoje `ensureBank` em `neo4j.js` **não cria nada**:
```js
export async function ensureBank(bankId, name) {
  const bank = validateBankId(bankId);
  return { id: bank, name: name || bank };   // ← no-op, não toca no Neo4j
}
```
Consequência: criar uma chave com um bank novo **não registra o bank no Neo4j**.

### B1. `ensureBank` real
Use **MERGE**, nunca CREATE — banks existentes têm dados e não podem ser sobrescritos:

```cypher
MERGE (b:Bank {id: $bank})
ON CREATE SET b.name = $name, b.source = 'zrouter', b.created_at = $now
RETURN b.id AS id, b.name AS name, b.created_at AS created_at
```

- `MERGE` na chave `id` (é o que o recall usa: `Memory.bank` casa com `Bank.id`)
- `ON CREATE` **somente** — se o bank já existe (ex.: `ViniciusMathias`, com `mission`,
  `background`, `disposition_json`, `config_json`, `overrides_json`), **não toque em nada**
- Envolva em try/catch: falha ao criar o bank **não pode** impedir a criação da chave
  (log estruturado, segue o fluxo)

### B2. `ensureMentalModel` real
Mesmo princípio:
```cypher
MERGE (mm:MentalModel {bank: $bank, id: $id})
ON CREATE SET mm.content = '', mm.created_at = $now, mm.source = 'zrouter'
RETURN mm.id AS id
```
- Shape: `MentalModel` tem `bank` + `id` e é lido em `mentalModelForProfile()` — confira no
  código antes de escrever
- `ON CREATE` apenas; mental models existentes (há 17) não podem ser sobrescritos
- try/catch, fail-open igual ao B1

### B3. Onde chamar
- **Criação** (`POST /api/keys`): já chama `ensureBank`/`ensureMentalModel` — passa a funcionar
  de verdade com B1/B2. Confirme que o bank usado é o `hindsightBankId` resolvido.
- **Edição** (`PATCH /api/keys/[id]`): verifique se hoje chama `ensureBank` quando o bank

## PARTE C — Dependências embutidas, mas NÃO obrigatórias (correção do dono)

**Princípio:** o repo traz as dependências **declaradas e prontas**, mas **subir é opt-in**.
Um deployment remoto (ex.: uma VPS que usa o Neo4j do zion-server pela rede) deve ser capaz
de rodar **só o zrouter**, apontando para um Neo4j externo — sem precisar remover nada do
compose nem editar arquivo nenhum.

### C1. `docker-compose.yml` (versionado) — bundled atrás de um profile

Este é o **único** comportamento correto e já foi validado com `docker compose config`:

```yaml
services:
  zrouter:
    # ...
    environment:
      # Aponta para QUALQUER Neo4j — local, bundled ou remoto (Tailscale/LAN).
      # Em uma VPS: NEO4J_HTTP_URL=http://<host-remoto>:7474 (o zion-server)
      NEO4J_HTTP_URL: ${NEO4J_HTTP_URL:-http://127.0.0.1:7474}
      NEO4J_DATABASE: ${NEO4J_DATABASE:-neo4j}
      NEO4J_USER: ${NEO4J_USER:-neo4j}
      NEO4J_PASSWORD: ${NEO4J_PASSWORD:-change-me-neo4j}
      OPEN_NOTEBOOK_URL: ${OPEN_NOTEBOOK_URL:-http://127.0.0.1:5055}
    depends_on:
      neo4j:
        condition: service_started
        required: false        # ← ausente do projeto NÃO bloqueia o zrouter
      open-notebook:
        condition: service_started
        required: false

  neo4j:
    image: neo4j:5.26-community
    profiles: ["bundled"]        # ← opt-in: NÃO sobe por padrão
    # ...

  surrealdb:
    image: surrealdb/surrealdb:v2
    profiles: ["bundled"]

  open-notebook:
    image: lfnovo/open_notebook:v1-latest
    profiles: ["bundled"]
```

**Comportamento resultante (validado):**
- `docker compose up -d` → sobe **só o zrouter** (usa o Neo4j que o `NEO4J_HTTP_URL` apontar)
- `docker compose --profile bundled up -d` → sobe o stack completo
- `required: false` no `depends_on` garante que a ausência dos serviços do profile
  **não impeça** o zrouter de subir (verificado: `docker compose config` aceita o serviço
  ausente com `required: false`)

Outros requisitos do compose:
- Portas com bind em **`127.0.0.1`**, nunca `0.0.0.0` — exceto se o dono pedir exposição
  explícita. Para uso remoto via Tailscale, o IP do Tailscale já dá o acesso.
- **Sem `container_name` colidindo**: use `zrouter-neo4j`, nunca `neo4j` puro (no zion-server
  já existe um container chamado `neo4j` de produção)
- `healthcheck` no Neo4j copiando a abordagem do compose de produção
  (`/opt/containers/neo4j/docker-compose.yml`), que funciona
- Defaults seguros em todas as credenciais (`${VAR:-change-me-...}`)

### C2. `docker-compose.override.yml` (NÃO versionado) — só o necessário neste servidor

Não use o override para "desativar" serviços — o profile já cuida disso. O override existe
apenas para injetar, **neste servidor**, as credenciais das fontes já existentes:

```yaml
services:
  zrouter:
    env_file:
      - ./.env
      - /opt/containers/neo4j/.env
      - /opt/containers/open-notebook/.env
```

⚠️ Se o arquivo já tiver mais conteúdo, **preserve** — só garanta que esses `env_file`
estejam presentes.

### C3. `.env.example` — documentar os dois modos

Deixe explícito, com exemplos:

```bash
# ── Como o zrouter encontra o Neo4j ─────────────────────────────
# Modo A — stack completo nesta máquina:
#   docker compose --profile bundled up -d
#   NEO4J_HTTP_URL=http://127.0.0.1:7474
#
# Modo B — usando um Neo4j que já existe (outra máquina, ex.: zion-server):
#   docker compose up -d          # sobe só o zrouter
#   NEO4J_HTTP_URL=http://<host-remoto>:7474
#
# O acesso remoto usa a rede Tailscale; não exponha o Neo4j na internet.
NEO4J_HTTP_URL=http://127.0.0.1:7474
NEO4J_DATABASE=neo4j
NEO4J_USER=neo4j
NEO4J_PASSWORD=change-me-neo4j

# As mesmas regras valem para o Open Notebook (Modo B):
# OPEN_NOTEBOOK_URL=http://<host-remoto>:5055
```
