## PARTE D — Preparação para o CUTOVER (20129 → 20128)

**Decisão do dono:** quando o ZRouter estiver funcional, ele **substitui** o 9Router atual e
passa a ocupar a **porta 20128**. Verificado que isso é favorável: o código já assume 20128 como
default (o padrão do upstream), então o cutover é uma troca de container, não uma reescrita.

### D1. Não quebre o dev agora
- Mantenha o compose de **dev na 20129** (`PORT: "20129"`). O cutover é uma operação à parte,
  feita pelo dono/EVE com o ZRouter já validado — **não antecipe**.
- **NÃO** altere a porta do container em execução. **NÃO** pare o 9Router de produção.

### D2. Deixe o cutover documentado e mecanizável
Crie `docs/CUTOVER-20128.md` descrevendo o procedimento exato, para que ele seja executado sem
improviso quando o dono aprovar:

1. **Pré-requisito:** ZRouter validado em 20129 (dashboard, fontes, memória, providers)
2. **Backup:** SQLite do 9Router (`/opt/containers/9router/data/db/data.sqlite`) e o do ZRouter
3. **Snapshot do que migra** — a decisão de dados é do dono, mas o documento deve listar:
   - providers/connections, combos, API keys, settings (incl. `globalInstructions`)
   - o que **não** migra automaticamente (nada de credencial em claro)
4. **Sequência:** parar o 9Router → subir o ZRouter com `PORT=20128` → validar health/rotas →
   rollback documentado (voltar o 9Router)
5. **Verificação pós-cutover:** `/api/health`, `/v1/models`, dashboard, uma geração real
6. **Rollback:** como reverter em <5 min

⚠️ **Não execute o cutover.** Apenas documente. A execução exige aprovação explícita do dono,
por ser uma parada de produção.

### D3. As skills continuam corretas
Os SKILL.md já apontam para `127.0.0.1:20128` — que é o endereço final. Não mude (ver A1).
