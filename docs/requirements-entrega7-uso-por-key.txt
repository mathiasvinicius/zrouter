## OBJETIVO (pedido do dono)

> "Quero histórico de uso por api key. Pra poder identificar facilmente as origens de uso."

Hoje o dashboard mostra uso **por provider**. O dono quer saber **qual chave** consumiu o quê —
para identificar de onde vem o uso (qual agente, qual cliente, qual perfil).

## O DADO JÁ EXISTE — falta a superfície

Verificado:

- `usageHistory.apiKey` **já é gravado** em cada requisição (149 linhas, ex. `sk-b910f70de...`)
- A tabela tem: `id, timestamp, provider, model, connectionId, apiKey, endpoint, promptTokens,
  completionTokens, cost, status, tokens, meta`
- `getUsageStats(period)` retorna `byProvider` — **e só isso**
- `grep -rn 'apiKey' app/src/app/(dashboard)/dashboard/usage/` → **vazio**: a UI nunca mostra

Ou seja: **não há migração nem coleta a fazer. É trabalho de agregação + UI.**

## PARTE A — API: agregação por chave

### A1. Estender `/api/usage/stats`
Em `src/app/api/usage/stats/route.js` → `getUsageStats(period)` (em `src/lib/usageDb`):

Adicione `byApiKey` ao retorno, no mesmo formato de `byProvider`:

```js
byApiKey: {
  "<key-fingerprint-ou-id>": { requests, promptTokens, completionTokens, cost, ... }
}
```

**Decisão de privacidade (importante):** a chave completa (`sk-...`) **não** deve trafegar para
a UI. Mapeie para um identificador estável e legível:
- prefira o **nome** da chave (`eve`, `OCR`, `ViniciusMathias`) resolvido via `apiKeys`
- se a chave não existir mais (deletada), use um rótulo `desconhecida-<hash curto>`
- nunca devolva a chave inteira; um prefixo (`sk-b91…`) é aceitável como secundário

Implemente uma resolução `apiKey → { id, name }` numa query só (join/Map), não N+1.

### A2. Filtro por chave
Aceite `apiKey` (nome ou id) como parâmetro opcional em `/api/usage/stats` e nos endpoints que
já filtram por período (`/api/usage/chart`, `/api/usage/history`). Com filtro, `totalRequests`,
`byProvider` e os totais refletem **apenas aquela chave**.

### A3. Série temporal por chave
Em `/api/usage/chart`, permita `groupBy=apiKey` além do agrupamento atual, para o gráfico poder
mostrar uma linha por chave.

## PARTE B — UI: a página de uso

### B1. Card/tabela "Uso por API key"
Na página `/dashboard/usage` (`src/app/(dashboard)/dashboard/usage/page.js` + `components/`):

Nova seção com uma linha por chave, ordenável, mostrando:
- **nome da chave** (e o perfil/banco associado, se houver — `hindsightBankId`)
- requisições, tokens (prompt/completion), **custo**
- último uso (timestamp)
- participação no total (barra ou %)

Siga o design system existente (`Card`, `SegmentedControl`, tokens de tema `brand-*`,
dark/light). **Não invente estilo novo** — copie a linguagem visual de `OverviewCards.js` e
`UsageTable.js`, que já existem na mesma pasta.

### B2. Filtro por chave na página
Um seletor (ex.: `SegmentedControl` ou dropdown) que filtra a página inteira por chave,
refletindo na URL (`?apiKey=...`) para ser compartilhável/recarregável — o componente já usa
`useSearchParams`/`useRouter`, siga esse padrão.

### B3. Ligação com a chave
Quando a linha corresponder a uma chave existente, torne-a clicável levando ao endpoint/perfil
dela (`/dashboard/endpoint` com a chave selecionada), fechando o ciclo "vejo o uso → vou na chave".

### B4. Onde a chave "não existe mais"
Uso de chaves deletadas continua aparecendo (histórico é histórico), agrupado sob o rótulo de
desconhecida. Deixe visualmente distinto (ex.: texto muted).

## COMMIT

Um commit único:
```
feat(usage): per-API-key usage history and filtering

The owner needs to see where usage comes from, not just which provider served it.
The data was already there — usageHistory.apiKey is written on every request — but
getUsageStats only aggregated by provider and the UI never looked at the key.

- getUsageStats: new byApiKey aggregate; the full key never reaches the client
  (resolved to the key's name, or a "unknown-<hash>" label for deleted keys)
- /api/usage/stats + /chart + /history accept an apiKey filter; /chart accepts
  groupBy=apiKey for one series per key
- /dashboard/usage: "Usage by API key" section (requests, tokens, cost, last use,
  share of total), a key filter reflected in the URL, and a link from each row to
  that key's endpoint page
- tests: usage-by-api-key
```
